# Product UI patterns for presenting anomalies, alerts and incidents (Datadog, Grafana/Alertmanager, Sentinel/Defender, Elastic, Splunk, CloudWatch, Google Cloud, New Relic, Google SecOps)

Scope note: these notes describe the *presentation layer* (how things are listed, grouped, scored, explained, tuned). Algorithm details are included only where the parameter is what the user tunes. "Screenshot described in words" = description of what the documented UI element shows, based on the doc text and the doc's own screenshot captions; I could not view the images themselves. Items I could not verify are flagged "(unverified)".

Target context reminder for the report writer: an internal daily-batch dashboard (tokens, DAU per product per day) reviewed by 1–3 analysts. A "transfer" note at the end of each section says which patterns carry over and which assume real-time event streams.

## Key Question 1 — Datadog: anomaly monitors (expected band, deviations, algorithms) and Watchdog stories/insights

### Takeaway
Datadog draws a gray "expected" band on the metric chart, flags points outside it, and lets the user tune the band width in standard deviations ("deviations"/"bounds", 2–3 recommended), the algorithm (basic/agile/robust, chosen by how seasonal/stable the metric is), direction, and trigger/recovery windows with a "% of points anomalous" threshold. Watchdog packages ML findings as plain-language alert cards (message + graph with toggleable "Expected Bounds" + timeline + tags + suggested next steps) with ongoing/resolved/expired status, surfaced via a pink binoculars icon in context and ranked "Insights" carousels.

### Cited Findings
- Chart presentation: "a metric is considered to be anomalous if it is outside of the gray anomaly band" — [Datadog Anomaly Monitor](https://docs.datadoghq.com/monitors/types/anomaly/)
- The `anomalies()` graph function overlays "a gray band on the metric showing the expected behavior of a series based on past" data; the `bounds` parameter is the "Width of the gray band. `bounds` can be interpreted as the standard deviations for your algorithm; a value of 2 or 3 should be large enough to include most 'normal' points." — [Datadog Algorithms functions](https://docs.datadoghq.com/dashboards/functions/algorithms/)
- Monitor "Deviations" parameter: "Controls the band width, measured in standard deviations"; "equivalent to the bounds parameter used in the anomalies function." — [Datadog Anomaly Monitor](https://docs.datadoghq.com/monitors/types/anomaly/)
- Direction: alert when values are "above or below," "above," or "below" the bounds. — [Datadog Anomaly Monitor](https://docs.datadoghq.com/monitors/types/anomaly/)
- Algorithms as user-facing presets: **Basic** "For metrics with no seasonal patterns; uses simple lagging rolling quantile computation"; **Agile** "For seasonal metrics expecting shifts; quickly adjusts to metric level shifts"; **Robust** "For stable seasonal metrics; slow, level shifts are considered anomalies." — [Datadog Anomaly Monitor](https://docs.datadoghq.com/monitors/types/anomaly/)
- Seasonality presets in plain language: Hourly "The algorithm expects the same minute after the hour behaves like past minutes"; Daily "The algorithm expects the same time today behaves like past days"; Weekly "The algorithm expects that a given day of the week behaves like past days." — [Datadog Anomaly Monitor](https://docs.datadoghq.com/monitors/types/anomaly/)
- "By default, the `robust` and `agile` algorithms use weekly seasonality, which requires three weeks of historical data to compute the baseline." ML algorithms need "at least three time as much historical data time as the chosen seasonality time." — [Datadog Algorithms functions](https://docs.datadoghq.com/dashboards/functions/algorithms/); [Datadog Anomaly Monitor](https://docs.datadoghq.com/monitors/types/anomaly/)
- Persistence filter: Trigger Window = "How much time is required for the metric to be anomalous before the alert triggers"; warning: "If the alert window is too short, you might get false alarms due to spurious noise." Recovery Window = "The amount of time required for the metric to no longer be considered anomalous, allowing the alert to recover." Thresholds = "The percentage of points within the trigger/recovery windows that must be anomalous for alerting." — [Datadog Anomaly Monitor](https://docs.datadoghq.com/monitors/types/anomaly/)
- UX rationale: Datadog "strongly recommends" building monitors in the UI because "customers benefit from the preview graph and automatic parameter tuning." — [Datadog Anomaly Monitor](https://docs.datadoghq.com/monitors/types/anomaly/)
- `outliers()` (cross-series comparison, "which series is unlike the others"): algorithms DBSCAN, MAD, scaledDBSCAN, scaledMAD; parameters `TOLERANCE` and `PERCENTAGE` ("The percentage of outlying points required to mark a series as an outlier (available only for MAD and scaledMAD algorithms)"); the function highlights "outliers series." — [Datadog Algorithms functions](https://docs.datadoghq.com/dashboards/functions/algorithms/)
- Watchdog Alert card contents: a plain-language "descriptive message about the anomaly," "A graph visually representing the detected anomaly," "A timeline describing when the anomaly occurred," "Associated tags showing the anomaly's scope," and an "Expected Bounds" toggle to "differentiate between expected and anomalous behavior"; the expanded pane may contain "Suggested Next Steps: Describes steps for investigation and triage" and associated monitors. — [Datadog Watchdog Alerts](https://docs.datadoghq.com/watchdog/alerts/)
- Watchdog status vocabulary: cards show whether an anomaly is "ongoing, resolved, or expired" ("expired" = over 48 hours continuous). — [Datadog Watchdog Alerts](https://docs.datadoghq.com/watchdog/alerts/)
- In-context surfacing: "When Watchdog detects an irregularity in an APM metric, the pink Watchdog binoculars icon appears" on service pages and metric graphs, linking to the alert card. Alert Explorer lets users "view alerts detected in a specific time range" up to six months back, with time range, keyword search and facets. — [Datadog Watchdog Alerts](https://docs.datadoghq.com/watchdog/alerts/)
- Noise management: users can "archive a Watchdog Alert" via a folder icon; archived ones are hidden but reachable via an "archived alerts" filter. — [Datadog Watchdog Alerts](https://docs.datadoghq.com/watchdog/alerts/)
- Watchdog alert types: APM error rate / latency / request volume; infrastructure (database and system metrics); log anomalies (pattern emergence, unexpected increases in error logs). — [Datadog Watchdog Alerts](https://docs.datadoghq.com/watchdog/alerts/)
- Watchdog Insights = "a recommendation engine that helps you identify and resolve issues"; shown as a carousel near the top of Log Explorer, APM services, RUM Explorer etc.; an error-outlier card shows "the field name" and "the proportion of errors and overall logs that the field contributes to"; a latency-outlier card shows "the latency distribution for spans containing the tag and the baseline for the rest of the data." Ranking: "the highest priority insights (based on `Insight type`, `State`, `Status`, `Start time`, `Anomaly type`) appear on the left." "View all" opens a side panel "containing a vertical list of Watchdog Insights"; hovering a card and clicking the filter icon makes "the page refreshes to show a list of entries corresponding to the insight." — [Datadog Watchdog](https://docs.datadoghq.com/watchdog/); [Datadog Watchdog Insights](https://docs.datadoghq.com/watchdog/insights/)

### Inferences
- Datadog's tuning UI is two-layered: a numeric knob (deviations) plus categorical presets (algorithm, seasonality, direction). The presets are described in plain-language expectations ("the same time today behaves like past days"), which is a transferable copywriting pattern for a day-kind baseline (weekday vs weekend).
- The "% of anomalous points in a window" threshold is a persistence filter that reduces single-point false alarms; in a daily-batch dashboard the analogue is "N of the last M days anomalous" or "2 consecutive days".
- Watchdog's card anatomy (one-sentence headline → chart with expected band → when/duration → scope tags → suggested next step) is a complete, transferable template for a "signal card".
- Transfer: expected band, deviations knob, algorithm presets, card anatomy, ongoing/resolved/expired, archive-with-filter all transfer. Trigger/recovery windows in minutes assume real-time streams; replace with day counts.

### Gaps
- The default value of "Deviations" in the monitor UI is not stated in the fetched docs (unverified; commonly 3 in the UI, but I could not confirm).
- I could not confirm whether Watchdog provides explicit "useful / not useful" feedback buttons from the docs fetched (the overview mentions feedback mechanisms only in passing).

## Key Question 2 — Grafana alerting UI, Grafana ML outlier/forecast, Prometheus Alertmanager grouping

### Takeaway
Grafana models alert state as Normal → Pending → Alerting → Recovering → Normal(Resolved), with Pending period and "Keep firing for" as anti-flap controls, and separates *labels* (identity, routing, grouping, silencing) from *annotations* (summary, description, runbook_url for humans). Alertmanager groups alerts by label set into one notification with group_wait 30s / group_interval 5m / repeat_interval 4h defaults, plus inhibition and silences. Grafana ML uses a three-level Low/Medium/High sensitivity preset for outliers and a 0.95 uncertainty interval for forecast bands.

### Cited Findings
- State vocabulary: "When an alerting condition is met, the alert instance enters the **Pending** state. It remains in this state while any alerting condition is met during the configured pending period." Lifecycle: "**Normal** -> **Pending** -> **Alerting**" then "**Alerting** → **Recovering** → **Normal (Resolved)**". — [Grafana alert rule evaluation](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/)
- Anti-flap: "You can set a **Keep firing for** period to avoid repeated firing-resolving-firing notifications caused by flapping conditions." "When the alert condition is no longer met during the **Alerting** state, the alert instance enters the **Recovering** state." Setting Keep firing for to zero skips Recovering. — [Grafana alert rule evaluation](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/); [Grafana What's new: Recovering state (2025-05-05)](https://grafana.com/whats-new/2025-05-05-grafana-managed-alert-rule--recovering--state/)
- Notifications are sent only on transitions: "1. When they transition to the **Alerting** state. 2. When they transition to **Normal** state and marked as `Resolved`." — [Grafana alert rule evaluation](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/)
- Non-data states: **No Data** "the alert rule query runs successfully but returns no data points"; **Error** "the alert rule fails to evaluate its query or queries successfully"; "Keep last state" option helps "mitigate temporary data source issues, preventing alerts from unintentionally firing, resolving, and re-firing"; `grafana_state_reason` annotation explains why evaluation state differs from alert state. — [Grafana state and health](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/state-and-health/)
- Labels vs annotations: labels are "unique identifiers of an alert instance"; "the complete set of labels for an alert is what uniquely identifies an alert instance"; notification policies use labels to "match alert instances and route them to contact points." Categories: user-configured (`severity`, `priority`, `team`, `service`), query labels, reserved (`alertname`, `grafana_folder`). Annotations "provide extra details for alert responders"; recommended: `summary` (concise explanation of what triggered), `description` (detailed context and recommended responses), `runbook_url` (operational guidance), `__dashboardUid__`/`__panelId__` (links to dashboards). Both "can use a template to include dynamic data from queries." — [Grafana labels and annotations](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rules/annotation-label/)
- Grafana ML outlier detection: DBSCAN "clusters data points based on their density and relative distance, and flags a series when its data points fall outside the largest cluster"; MAD "evaluates each data point against the rolling 24-hour median and flags a series when the deviation exceeds the configured sensitivity threshold." Sensitivity is a preset: Low "Flags only the most extreme deviations", Medium balanced, High "Flags smaller deviations"; guidance is to raise it if outliers are missed and lower it to cut false positives. The Summary "displays all returned series and highlights the series containing outliers"; each detector emits a `<outlier_detector>:outliers` metric usable in alert rules. — [Grafana ML Outlier detection](https://grafana.com/docs/grafana-cloud/alerting-and-irm/machine-learning/outlier-detection/)
- Grafana ML forecasting: produces `<forecast_metric_name>:predicted` and `:actual`; "Uncertainty Interval Width" default 0.95, i.e. "95% of future data is expected to fall within the predicted interval"; "the model uses 90 days of training data" by default; it "automatically detects daily and weekly seasonality when the training data contains at least two days or two weeks of data respectively"; users can configure holidays; alerts can be based on actual vs forecast bounds. — [Grafana ML Forecasts](https://grafana.com/docs/grafana-cloud/alerting-and-irm/machine-learning/forecasts/)
- Alertmanager concepts: "Grouping categorizes alerts of similar nature into a single notification" (example: hundreds of instances losing DB connectivity → one notification grouped by cluster and alertname); "Inhibition is a concept of suppressing notifications for certain alerts if certain other alerts are already firing"; "Silences are a straightforward way to simply mute alerts for a given time," configured via matchers in the web UI. — [Prometheus Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/)
- Alertmanager route timing: `group_by` = "the labels by which incoming alerts are grouped together" (special value `'...'` aggregates by all labels, i.e. disables grouping); `group_wait` "how long to wait before sending the first notification for a new group of alerts" default `30s`; `group_interval` "how long to wait before sending subsequent notifications for an existing group of alerts after group_wait" default `5m`; `repeat_interval` "how long to wait before repeating the last notification" default `4h`. Inhibit rules use `source_matchers`, `target_matchers`, `equal`. — [Alertmanager configuration](https://prometheus.io/docs/alerting/latest/configuration/)

### Inferences
- The label/annotation split is a clean data-model rule for a small dashboard: structured dimensions (product, metric, day_kind, severity) drive grouping/filtering/muting; free-text fields (summary, description, runbook link) are for the human.
- Pending/Keep-firing map directly onto daily batches as "flag only after N days" and "keep a signal visible for N days after it stops", which addresses the "new vs ongoing" question without real-time state.
- Grafana ML's Low/Medium/High sensitivity preset is evidence that mature vendors offer categorical sensitivity for ML detectors even when the underlying parameter is numeric.
- Transfer: states, labels/annotations, runbook link, group-by-labels, silence-with-matcher all transfer; group_wait/group_interval timing and inhibition between simultaneous alerts assume streams (inhibition can be approximated by "suppress per-product signals when the all-products signal fires").

### Gaps
- Grafana docs fetched do not describe the state colors/badges in the alert list UI (unverified).
- Alertmanager docs fetched do not describe the Alertmanager web UI layout (group headers, expand/collapse) in detail (unverified).

## Key Question 3 — Microsoft Sentinel (incidents vs alerts, grouping, severity, entity pages, investigation graph, Fusion) and Defender XDR "alert story"

### Takeaway
Sentinel separates *alerts* (evidence) from *incidents* (case files that aggregate alerts, entities, severity, status, tactics); rules group up to 150 alerts into one incident by entity match within a time window and can re-open closed incidents. Severity is four levels with explicit definitions (Informational/Low/Medium/High), status is New/Active/Closed with a mandatory closing classification, and the incident page shows a timeline, similar incidents (with "similarity reason"), entities, top insights, and an investigation graph. Fusion turns many low-fidelity alerts into "low-volume, high-fidelity, high-severity" incidents. Defender XDR's alert page leads with an "alert story" (chronological chain of events in a process tree) plus a details pane, and provides alert tuning (hide/resolve/set-as-behavior).

### Cited Findings
- Incidents are "files that contain an aggregation of all the relevant evidence for specific investigations"; "Incidents inherit the entities ... contained in the alerts, as well as the alerts' properties, such as severity, status, and MITRE ATT&CK tactics and techniques." — [Sentinel: Investigate incidents](https://learn.microsoft.com/en-us/azure/sentinel/investigate-incidents)
- Incidents grid page layout: top toolbar with "the counts of open incidents, whether new or active, and the counts of open incidents by severity"; central grid "filtered by the filtering controls at the top of the list, and a search bar"; side "details pane that shows important information about the incident highlighted in the central list, along with buttons for taking certain specific actions." Triage actions directly from the pane: assign Owner, change Status (New → Active → Closed), change Severity, add tags, add comments. Default search covers "Incident ID, Title, Tags, Owner, and Product name." — [Sentinel: Navigate and triage incidents](https://learn.microsoft.com/en-us/azure/sentinel/incident-navigate-triage)
- Closing classification is mandatory: "True Positive – suspicious activity", "Benign Positive – suspicious but expected", "False Positive – incorrect alert logic", "False Positive – incorrect data", "Undetermined". — [Sentinel: Navigate and triage incidents](https://learn.microsoft.com/en-us/azure/sentinel/incident-navigate-triage)
- Severity definitions used in the rule wizard: **Informational** "No impact on your system, but the information might be indicative of future steps planned by a threat actor"; **Low** "The immediate impact is minimal..."; **Medium** "The threat actor could have some impact on the environment with this activity, but it would be limited in scope or require additional activity"; **High** "The activity identified provides the threat actor with wide ranging access ... or is triggered by impact on the environment." — [Sentinel: Create scheduled analytics rules](https://learn.microsoft.com/en-us/azure/sentinel/create-analytics-rules) (the `detect-threats-custom` URL redirects here)
- Alert threshold as "sensitivity": "Use the **Alert threshold** section to define the sensitivity level of the rule," e.g. "Generate alert when number of query results … Is greater than … 100". Event grouping: "Group all events into a single alert (default)" vs "Trigger an alert for each event". Suppression: "Stop running query after alert is generated" for up to 24 hours. Results simulation: "Test with current data" shows a graph of what the rule would have produced. — [Sentinel: Create scheduled analytics rules](https://learn.microsoft.com/en-us/azure/sentinel/create-analytics-rules)
- Alert grouping into incidents: "if you want a single incident to be generated from a group of up to 150 similar or recurring alerts," enable "Group related alerts, triggered by this analytics rule, into incidents"; "Limit the group to alerts created within the selected time frame"; group options: "Group alerts into a single incident if all the entities match" (recommended), "Group all alerts triggered by this rule into a single incident", "Group alerts into a single incident if the selected entities and details match"; "Re-open closed matching incidents" toggle. "Up to 150 alerts can be grouped into a single incident"; overflow creates a new incident with the same details. — [Sentinel: Create scheduled analytics rules](https://learn.microsoft.com/en-us/azure/sentinel/create-analytics-rules)
- Incident details page widgets: **Incident timeline** ("timeline of alerts and bookmarks ... help you reconstruct the timeline of attacker activity"), **Similar incidents** ("up to 20 other incidents that most closely resemble the current incident"; "The reasons an incident appears in the similar incidents list are displayed in the **Similarity reason** column"; hover shows common entities, rule name, or details), **Entities**, **Top insights** (curated queries, time frame "from 24 hours before the earliest alert in the incident until the time of the latest alert"). — [Sentinel: Investigate incidents](https://learn.microsoft.com/en-us/azure/sentinel/investigate-incidents)
- Visual distinction of out-of-scope evidence in the entity timeline: "Alerts that aren't part of the incident are displayed differently: the shield icon is grayed out, the severity color band is dotted line instead of a solid line, and there's a button with a plus sign on the right side of the alert's row." Entity Timeline card "is limited to alerts and activities from the prior seven days." — [Sentinel: Investigate incidents](https://learn.microsoft.com/en-us/azure/sentinel/investigate-incidents)
- Investigation graph: "an illustrative map of the entities directly connected to the incident's alerts"; hover on an entity reveals "exploration queries"; related alerts "appear connected to the entity by dotted lines"; "the graph gives you a parallel timeline"; supports "incidents up to 30 days old"; the doc admits "The downside of the graph is that you end up having to switch contexts a great deal more." — [Sentinel: Investigate incidents](https://learn.microsoft.com/en-us/azure/sentinel/investigate-incidents)
- Activity log/comments: autorefreshing audit log; comments limited to 30,000 chars, 100 per incident. — [Sentinel: Investigate incidents](https://learn.microsoft.com/en-us/azure/sentinel/investigate-incidents)
- Fusion: "a correlation engine based on scalable machine learning algorithms, to automatically detect multistage attacks ... by identifying combinations of anomalous behaviors and suspicious activities"; "These incidents comprise two or more alerts or activities. By design, these incidents are low-volume, high-fidelity, and high-severity." Presented "as **Fusion incidents** on the Microsoft Sentinel **Incidents** page and not as **alerts**." Example: five alerts of severity informational/medium/informational/low/informational on one host within a time frame become one incident "Multiple alerts possibly related to Ransomware activity detected"; emerging-threat incidents are titled "Possible multistage attack activities detected by Fusion." Scenario names follow the pattern "X *following* Y" / "X *coinciding with* Y". Fusion is disabled when onboarded to the Defender portal (replaced by the XDR correlation engine). — [Sentinel: Fusion](https://learn.microsoft.com/en-us/azure/sentinel/fusion)
- Defender XDR: "alerts represent individual pieces of evidence that Defender XDR correlates together to form incidents ... Incidents tell the whole attack story." Alerts queue default: "the new and in progress alerts from the last seven days. The most recent alert is at the top"; filters include Severity, Status, Categories, Service/detection sources, Tags, Entities. Tags: "Custom tags use the white background while system tags typically use red or black background colors" (system tags: type of attack, automatic actions, Defender Experts, critical assets). — [Defender XDR: Investigate alerts](https://learn.microsoft.com/en-us/defender-xdr/investigate-alerts)
- Alert page anatomy: "Alert story, which is the chain of events and alerts related to this alert in chronological order" and "Summary details"; "The alert story displays all assets or entities related to the alert in a process tree view ... Assets in the alert story are expandable and clickable"; "The alert story section may contain more than one alert." — [Defender XDR: Investigate alerts](https://learn.microsoft.com/en-us/defender-xdr/investigate-alerts)
- Manage alert pane: status (New, Resolved, In progress), assignee, classification **Not Set** / **True positive** / **Informational, expected activity** ("technically accurate, but represent normal behavior or simulated threat activity") / **False positive** ("you generally don't want to see these alerts again"); "View similar alerts" lets you classify related alerts at once; "Recommendations" tab shows how similar alerts were resolved before. — [Defender XDR: Investigate alerts](https://learn.microsoft.com/en-us/defender-xdr/investigate-alerts)
- Alert tuning actions: **Hide alert**, **Resolve alert**, **Set as behavior** ("Converts matching signals into behaviors. They won't appear in the alert queue or trigger incidents"); built-in tuning rules "help reduce reporting noise from common benign activity." Entra ID Protection alert default changed to "High-risk detections only" with options "High + Medium" or "All detections." — [Defender XDR: Investigate alerts](https://learn.microsoft.com/en-us/defender-xdr/investigate-alerts)

### Inferences
- The alert→incident two-tier model is the clearest cross-vendor answer to "group many alerts into one": the grouping key is shared entity (here: product, or metric family), bounded by a time window and a max count, with an option to re-open the previous group when the condition recurs.
- Mandatory close-reason taxonomies (true/benign/false positive) double as a feedback loop for tuning and give the "informational vs actionable" distinction a persistent label.
- "Similarity reason" and "shown dotted if outside this incident" are small but valuable explanation affordances: always show *why* something is related.
- Transfer: incident grouping with entity key + window + cap, 4-level severity with written definitions, close classification, similar-incidents with reasons, counts-by-severity header all transfer. Investigation graph, process trees and MITRE tactics assume event-level security data and do not transfer.

### Gaps
- The exact column list of the Sentinel incidents grid (e.g., "Product names", "Alerts" count) is only visible in screenshots not fetched; column names above are from the doc text about search parameters (partially verified).

## Key Question 4 — Elastic Security (alerts table, rule risk score, entity risk) and Kibana ML Anomaly Explorer (0–100 score, severity bands, swimlanes, typical vs actual, influencers) — DETAILED

### Takeaway
Kibana ML normalizes every anomaly to a 0–100 score where 100 is "the biggest anomalies the job has seen to date," buckets it into four named severities (critical 75–100, major 50–75, minor 25–50, warning 0–25) each with its own color, shows them as a heatmap "swim lane" per time bucket (overall lane plus one lane per entity/influencer), lists them in an Anomalies table with "typical vs actual" values and a severity-threshold filter, and explains each one with single-bucket impact, multi-bucket impact and anomaly characteristics. Elastic Security uses a parallel scheme for detection alerts: severity (Low/Medium/High/Critical) with default risk-score ranges (0–21/22–47/48–73/74–100), an alerts table with open/acknowledged/closed status and "group by up to three fields", an alert flyout that shows a generated "reason" sentence, highlighted fields, correlations and prevalence, and an entity risk score 0–100 aggregated from alerts with five levels.

### Cited Findings — Kibana ML anomaly detection
- Score semantics: "Anomaly scores are in the range of 0 and 100. The values close to 100 signify the biggest anomalies the job has seen to date." Scores are relative: "the lowest probabilities historically for the job get the highest anomaly scores." — [Elastic ML: Anomaly explanation](https://www.elastic.co/guide/en/machine-learning/current/ml-ad-explain.html); [Elastic blog: anomaly scoring — how it works](https://www.elastic.co/blog/machine-learning-anomaly-scoring-elasticsearch-how-it-works)
- Three score levels: **record score** (unusualness of one instance), **influencer score** (which entities are "to blame" for anomalies in a bucket, aggregated across detectors), **bucket score** (overall anomalousness of a time window, depending on "the magnitude of the individual anomalies (records) occurring within that bucket" and their count). — [Elastic blog: anomaly scoring](https://www.elastic.co/blog/machine-learning-anomaly-scoring-elasticsearch-how-it-works)
- Severity bands: Critical 75–100, Major 50–75, Minor 25–50, Warning 0–25; "Each severity level receives a distinct color designation in visualizations." — [Elastic blog: anomaly scoring](https://www.elastic.co/blog/machine-learning-anomaly-scoring-elasticsearch-how-it-works); same thresholds restated by [Ashnik (third-party)](https://www.ashnik.com/?p=41490)
- Colors in the swim lane (getting-started doc): "blue indicates low, yellow indicates medium, and red indicates high severity, with different shades representing varying levels within each category"; "Red highlights high-scoring values while blue indicates low-scored ones." — [Elastic ML: Getting started — view results](https://www.elastic.co/guide/en/machine-learning/current/ml-gs-results.html)
- Alerting default threshold: "The default severity threshold is 75 which means every anomaly with an `anomaly_score` of 75 or higher triggers the associated action." Rule result types: "bucket, record, or influencer results." Recommendation: alert on bucket score because it is "rate limited, meaning that you'll never get more than 1 alert per bucket_span." — [Elastic ML: Configuring alerts](https://www.elastic.co/guide/en/machine-learning/current/ml-configuring-alerts.html); [Elastic blog: anomaly scoring](https://www.elastic.co/blog/machine-learning-anomaly-scoring-elasticsearch-how-it-works)
- Swim lanes: Anomaly Explorer shows swim lanes for influencer values ("You can also explore swim lanes that correspond to the values of an influencer"); by default lanes are sorted by entities with the highest anomaly scores; clicking a cell shows details for that time interval; with a partition field "you can choose to see separate swim lanes for each client IP or response code." Each bucket's score is "a statistically aggregated and normalized view of the combined anomalousness." — [Elastic ML: View results](https://www.elastic.co/guide/en/machine-learning/current/ml-ad-view-results.html); [Elastic ML: Getting started — view results](https://www.elastic.co/guide/en/machine-learning/current/ml-gs-results.html)
- Top influencers panel: "a list of the top influencers for all of the detected anomalies" with maximum and total aggregated anomaly scores, to "narrow down the contributing factors." — [Elastic ML: View results](https://www.elastic.co/guide/en/machine-learning/current/ml-ad-view-results.html)
- Anomalies table: presents "key details about each anomaly such as time, typical and actual values, and probability," with an **Actions** menu to open source data; severity filter: "By default, the table contains all anomalies that have a severity of 'warning' or higher in the selected section of the timeline. If you are only interested in critical anomalies, for example, you can change the severity threshold for this table." — [Elastic ML: View results](https://www.elastic.co/guide/en/machine-learning/current/ml-ad-view-results.html); [Elastic ML: Getting started — view results](https://www.elastic.co/guide/en/machine-learning/current/ml-gs-results.html)
- "Typical" value definition: "The typical value is the median value of the probability distribution for the bucket." — [Elastic ML: Anomaly explanation](https://www.elastic.co/guide/en/machine-learning/current/ml-ad-explain.html)
- Single Metric Viewer band: "The shaded blue area represents the bounds for the expected values. The area between the upper and lower bounds are the most likely values for the model, using a 95% confidence level." Zoom in/out buttons beside the date picker. — [Elastic ML: Getting started — view results](https://www.elastic.co/guide/en/machine-learning/current/ml-gs-results.html); [Elastic ML: View results](https://www.elastic.co/guide/en/machine-learning/current/ml-ad-view-results.html)
- Anomaly explanation section: "helps you to interpret a given anomaly by providing further insights about its type, impact, and score." ### Inferences
- The Kibana ML pattern is a complete, coherent scheme and is the most directly reusable for a batch dashboard: (1) normalize to 0–100 relative to the series' own history, (2) four named bands with fixed cut points and one color per band, (3) a heatmap of day × entity colored by max score, (4) a table of top anomalies with actual vs typical, (5) a severity-threshold selector defaulting to "warning or higher" for browsing but "critical (75)" for notifications, (6) a short explanation block (spike/dip, single- vs multi-bucket, length).
- "Multi-bucket impact" (12-bucket context) is the ML analogue of "ongoing vs one-off"; marking it with a different glyph (cross vs dot) is a cheap visual distinction.
- Renormalization implies that a day's score can change after later days arrive; a batch dashboard that recomputes history should show "score as of today" and be explicit that past scores may shift.
- Elastic Security's "reason" sentence (auto-generated from the event) and "prevalence" (how common is this value in the last 30 days) are two low-cost explanation widgets that transfer to usage data (e.g., "tokens for product X on 2026-10-01 were 3.2× the typical weekday value; last comparable value: 2026-08-15").
- Entity risk aggregation (sum of weighted recent alerts → 0–100 → 5 levels, retained hourly) transfers as a per-product "attention score" that decays when no new signals appear.
- Transfer: everything in the ML list transfers; alerts-table grouping and status workflow transfer at small scale; correlations by session/process ancestry and threat intel do not.

### Inferences (recommended borrowings for a 1–3 analyst, daily-batch usage dashboard)
1. Chart: draw the expected band (shaded) per product/metric with the day's actual point; color breaches by severity band, not just red; add a toggle to hide the band (Watchdog) and a "typical vs actual, ×N" label (Elastic).
2. Scoring: normalize each detector to 0–100 against that series' own history (Elastic), bucket into 4 named levels at 25/50/75 with one fixed color each and a one-line written definition per level (Sentinel/Elastic style). Use a ≥75 default for "needs a look", warning-and-above for browsing.
3. Sensitivity: expose ONE preset control (Low/Medium/High, as in Grafana ML) that maps internally to the SD/bounds number, and show the numeric mapping in a tooltip; keep direction (above/below/both) per metric.
4. Grouping: a "signal" = one detector × product × day; a "finding/incident" = signals sharing product (entity) within a window (e.g., 7 days), capped, re-opened if it recurs (Sentinel). Show a day × product heatmap colored by max score (Elastic swim lane) and the Splunk-style timeline of contributing signals when a finding is opened.
5. States for batch cadence: New (first day flagged), Ongoing (flagged ≥2 consecutive days; Grafana "Pending"→"Alerting" analogue), Recovering (not flagged today but within keep-visible window), Resolved/Expired (auto-close after N days, Google 7-day, Watchdog 48 h analogues). Default list view = New + Ongoing, newest first (Defender).
6. Informational vs actionable: use the lowest level ("Informational/Warning") for "record but do not notify"; let analysts close with a reason taxonomy (true/benign/false positive) and feed benign/false reasons back into tuning (CloudWatch reasons "too wide/narrow/planned event").
7. Explanation block per finding: one-sentence reason ("Tokens for X on Mon 2026-09-29 were 3.1× the typical Monday; above the band for 2 days"), typical vs actual numbers, baseline description (which days, excluded holidays), related findings with similarity reason, and a link to a runbook/notes.
8. Patterns that do NOT transfer or need adaptation: minute-scale trigger/recovery windows, group_wait/inhibition timing, investigation graphs/process trees, entity risk based on security alerts, snooze-by-notification (replace with mute-until-date per product/metric).
