# ChatGPT Usage Dashboard — 集計JSON版仕様書

## 1. 目的

ChatGPT管理画面から出力した日次集計JSONを管理者が手動アップロードし、ワークスペース全体の利用推移と異常兆候を確認できるダッシュボードを提供する。

監査ログと会話本文は扱わない。個人別分析では管理者が指定したユーザー識別子と集計トークン数だけを扱う。表示する異常は調査のきっかけとなる統計的な兆候であり、不正利用を断定するものではない。

## 1.1 設計の中心

分析担当者は、データに含まれない外部要因（休日出勤していた人がいる、今週はハッカソンがあった、など）を知っている。感度は、その要因を加味して「この前提ならどう見えるか」を試すためのレンズであり、上げる・下げるは判断の一部であって設定の調整ではない。

このツールの本分は次の2点である。

1. 前提の切り替えをできるだけ少ない操作で済ませること。
2. 切り替えた結果「何が分かったか」を明確に示すこと。緩い見方でも残る日はどれか、厳しく見て初めて現れる日はどれか。

前提を変えたときは、その前提で見えるものだけを示す。前提を変える前に見えていたものを薄く残す、数値を網羅して列挙する、といった表示は目的に反する。機能を足す前に、分析担当者が何を知りたいか、どの前提で見たいかを先に確かめる。

## 2. MVPスコープ

- `chart_key` が `active-users` と `tokens` のAnalytics JSONは1つずつ、または2つ同時にアップロードできる。各指標を独立して保存し、単独でもすぐにグラフ・分析へ反映する。期間の一致は要求しない。
- 画面のファイル選択はJSONのみとし、旧CSV形式はAPI互換用として同種2ファイルの組合せに限り受け付ける。
- 個人別分析では、対象ユーザーで絞り込んだ `chart_key: "tokens"` のJSONとユーザー識別子をアップロードする。
- `series` 内にChat・Codex・Workが各1つあることと、`rows` の開始日・終了日・系列値を検証して開始日をキーに結合する。
- UTF-8 JSON、正しい `chart_key`、非負整数、日付の一意性を検証する。
- 取込元JSONを加工せず保存し、正規化データは日付・指標単位で冪等に置換し、未アップロードの指標を保持する。
- ローカルでは `./data` 配下をストレージとして使用する。
- ダッシュボードは保存済みデータだけを読み、OpenAI APIへアクセスしない。
- Docker Composeでダッシュボードを実行できる。
- Dashboardおよびcollectorコンテナはroot以外のユーザーで実行する。

Chat/Codex/Workのアクティブユーザーには同一人物が重複する可能性があるため、製品間の値は合算しない。全体DAUが必要な箇所では「製品別DAUの最大値」を参考値として明記する。

## 3. 画面要件

- 画面は「推移」「インサイト」「個人別」「取込と設定」の4つに分け、起動時は「推移」を表示する。推移のKPI右端「インサイト（優先）」はインサイトの件数を示し、クリックでその画面へ移動する。JSON取込は推移に置く。
- インサイト: 最終データ日・経過日数・保存日数・基準・判定保留日数の状態行、取込停止の警告、検知器設定エラー。日を「優先して確認」「次に確認」「参考」の3段に分けた順位表を示し、各日に区分・DAU・総トークン、初出／継続N日目、観点ごとの1文（実測・普段・倍率・判定ライン）、参考観点の折りたたみ、確認済み表示、「確認済みにする／未確認に戻す」、「グラフで見る」（観点ごとの判定経緯を示す小グラフのフローティング表示）を置く。
- 取込と設定: 休日・平日の手動設定一覧と解除、判定に使っている観点とパラメータ、個人別の参考上限設定。
- JSONアップロード: 1つの「アップロードして分析」ボタンから1ファイルまたは複数ファイルを選択後、自動送信する。`chart_key` から種類を自動判定し、取り込んだ指標を直ちに表示する。未登録の指標は「—」またはデータなしと表示する。
- 取込状態: 最終成功日時、対象期間、日数、エラー状態
- KPI: DAU登録済みの最新日の製品別最大DAU、期間総トークン、トークン登録日数で割った日平均トークン、検出アラート数
- Chat/Codex/Work別の日次アクティブユーザー推移
- Chat/Codex/Work別の日次トークン消費量推移
- 両推移を折れ線グラフで表示し、グラフ上のドラッグで分析期間を指定
- 期間リセット操作で取込済みの全期間へ戻す
- 推移: 異常分析グラフの見出しに感度（低・やや低・標準・やや高・高、ブラウザごとに保存）を置き、変更時に出なくなった日・新たに出た日を表示する
- 日次表の平日・休日区分（クリックで上書き）と、その日の兆候件数
- 総トークンの異常分析グラフ（実測値、同じ区分の中央値、判定ライン、検出点、参考点）
- `?` アイコンのホバー／フォーカスで判定条件を表示
- 日次データ表
- 個人別分析では対象ユーザー名またはメールアドレスと、そのユーザーで絞り込んだトークンJSONを取り込む。
- 保存済みユーザーを選択し、期間総量、日平均、最新値、異常件数、製品別推移、異常分析、日次表を表示する。
- 個人別のCodex + Workトークンから、5時間枠・週次枠への到達相当回数と声かけ目安を表示する。
- 設定画面で5時間・週次の参考上限を変更し、初期値へリセットできる。
- 個人の日次表にCodex + Work、5時間枠消費率、到達相当回数を表示する。
- 個人の週次表を月曜から日曜で集計し、製品別トークン、Codex + Work、週次枠消費率、到達相当回数を表示する。
- 右上の保存データ履歴は両方の分析タブで表示し、同じ画面内に全体データと個人データの履歴を分けて表示する。
- 個人別JSONの保存履歴に取込日時、ユーザー、対象期間、日数、サイズ、SHA-256を表示する。

## 4. 異常判定

異常判定は差し替え可能な「検知器」の集合として実装する。検知器は `app.detectors.Detector` を継承したクラスで、`config/detectors.toml` から有効/無効・パラメータ・独自モジュールを指定する。設定はリクエストごとに読み込み、誤りがあればその検知器だけをスキップして `detector_errors` で通知する。

共通の前提:

- 指標ごとに実測値のある日のみを使い、未登録値を0として扱わない。
- 各日を平日・休日に区分し、基準は同じ区分の日だけから計算する。土日は休日、平日はDAU（DAUがなければトークン）が平日中央値の半分以下なら休日と推定する。閲覧者は日単位で区分を上書きでき、その設定はブラウザの `localStorage` にのみ保存し、`holidays`・`workdays` パラメータで送信する。
- 全期間表示では各日の直前28日のうち同じ区分の日を基準とし、5日に満たない日は判定保留として件数を返す。異常と判定した日は以後の基準から除外する。
- 分析対象期間を指定した場合、KPI、グラフ、表をその期間に限定し、選択期間内の同じ区分の日の中央値とMADで再計算する。
- 感度 `sensitivity`（0.25〜4.0、既定1.0）は閲覧者ごとの値で、各検知器の判定値（Zスコア、最小量、比率）をこの値で割る。閾値は目安であり、最終判断は複数の兆候を合わせて行う分析担当者に委ねる。
- インサイトの順位は感度1.0で計算し、日ごとに「その日に反応し始めた検知器数×10 + 前日から継続している検知器数×4 + 高があれば5 + 直前14日に無いパターンなら3」をスコアとする。上位5日のうち検知器2つ以上・高・初出のいずれかを満たす日を「優先して確認」、その他の非参考を「次に確認」、参考のみと確認済みの日を「参考」にする。`group = "operations"` の検知器（データ途絶）は観点ではなく状態として返す。
- 確認済みの記録は `date`・`kind`（checked / cleared）・`recorded_at` を追記保存し、日付ごとに最新の記録を採用する。
- シグナルは `detector`、`type`、`severity`（high/medium/info）、`metric`、`product`、`date`、`value`、`baseline`、`threshold`、`score`、`reason` を持つ。

組み込み検知器（既定値）:

- `token_spike`: 総トークン・製品別トークンが上振れかつロバストZスコア3.5以上（MADが0なら中央値の2倍以上）。Z7以上は高。Z2以上の上振れは参考。製品ごとの最小トークン量未満は無視。
- `tokens_per_user`: 製品別トークン÷同製品DAUが上振れかつZ3.5以上、かつ1人あたり500万tokens以上。Z6以上は高。
- `dau_change`: 製品別DAUのロバストZスコア絶対値が3.5以上かつ中央値との差が2人以上（MADが0なら2倍以上または半分以下）。
- `dau_increase`: 製品別DAUが同じ区分の直前28日の最大を上回る（参考）。
- `holiday_usage`: 休日の総トークンが平日中央値の50%以上かつ100万tokens以上。
- `stale_data`: 最終データ日から3日を超えて経過（参考、期間指定時は判定しない）。

履歴が短い期間や継続的な変化は検出しにくい。アラートは統計的な兆候として表示し、業務事情と合わせて確認する。

### 4.1 利用枠到達の推定

- 対象はWork/Codexと同じ利用枠を消費する `Codex + Work` とし、Chatは除外する。
- 非公式参考初期値は5時間26,300,000 tokens、週次173,000,000 tokensとする。
- 5時間到達相当回数は、各日合計を5時間参考上限で割った整数部分の合計とする。
- 週次到達相当回数は、月曜始まりの各週合計を週次参考上限で割った整数部分の合計とする。
- 週次参考上限の80%以上となった週数も表示する。
- 日次・週次とも80%以上100%未満を「接近」、100%以上を「到達相当」として表示する。
- 週次到達が1回以上、または5時間到達相当が2回以上なら声かけ目安を「高」とする。
- 5時間到達相当が1回以上、80%以上の週がある、または最大週が60%以上なら声かけ目安を「中」とする。
- 参考上限は閲覧者のブラウザの `localStorage` にだけ保存し、バックエンドへ送信しない。
- この値は非公式の公開実測に基づく推定であり、実際の制限到達を断定しない。

## 5. データ配置

```text
data/
  raw/<run-id>/active-users.json
  raw/<run-id>/tokens.json
  raw/<run-id>/individual-tokens.json
  raw/<run-id>/individual-import.json
  normalized/workspace-usage.jsonl
  normalized/dispositions.jsonl
  normalized/individual-usage.jsonl
  state/import.json
  state/individual-import.json
```

- rawは追記専用とし、再調査と正規化処理の修正に利用する。
- normalizedは `date` を論理キーとして再取込時に置換する。
- 個人別normalizedは `user_id + date` を論理キーとして再取込時に置換する。ユーザー名またはメールアドレスを正規化した値のSHA-256から `user_id` を生成する。
- stateには秘密情報を保存しない。
- アップロード上限は1ファイル5 MiBとする。

## 6. API

- `POST /api/import`: multipartの `files` 1〜2項目を受け取り、各JSONの `chart_key` から種類を判定する。各JSONを独立して検証・正規化し、日付・指標ごとに保存済みデータへ統合する。全ファイルの検証完了後に保存する。旧形式の `active_users_file`・`tokens_file` 項目も互換用に受け付ける。
- `GET /api/dashboard`: 保存済み集計と異常兆候を返す。`holidays`・`workdays`（カンマ区切り日付）で区分を上書きし、`sensitivity` で感度を指定できる。応答には `detectors`（設定済み検知器）、`detector_errors`、`pending_days`、各日の `day_kind`・`day_kind_source` を含む。
- `GET /api/detectors`: 設定済み検知器の一覧（id、表示名、説明、パラメータ）と設定エラーを返す。
- `GET /api/triage`: インサイトの内容（状態、today / week / reference の各リスト、設定エラー）を返す。`holidays`・`workdays` を受け付け、感度には依存しない。
- `GET /api/context`: `date` の前後（既定 35日前〜7日後）の日次行を区分つきで返す。観点ごとの小グラフに使う。
- `POST /api/dispositions`: JSON `{date, kind}`（kind は checked / cleared）を受け取り確認済みの記録を追記保存する。不正な値はHTTP 400。
- `GET /health`: ヘルスチェックを返す。
- `POST /api/individual/import`: ユーザー識別子と個人別トークンJSONを取り込む。
- `GET /api/individual`: ユーザー一覧と選択ユーザーの集計を返す。`holidays`・`workdays`・`sensitivity` を受け付ける。
- `GET /api/individual/imports`: 個人別JSONの保存履歴を返す（以前のCSV履歴も含む）。
- 入力不備はHTTP 400、ファイル上限超過はHTTP 413で返す。

## 7. セキュリティ

- `.env`、`data/`、実データJSONをGit管理しない。
- アップロード名を保存パスに使用せず、固定ファイル名で保存する。
- Dockerイメージに `.env` と利用データを含めない。
- MVPのWeb画面には認証を含めず、ローカルホスト向けとする。本番ではCognito等を必須とする。
- 個人識別子を含むため、本番では保存時暗号化、認証、最小権限、保持期間を必須とする。

## 8. 非機能要件

- 同じ日付の再取込で正規化レコードが重複しない。
- 取込失敗時に既存の正規化データを変更しない。
- 実データなしでfixtureを使ったテストを実行できる。
- Python 3.12、Docker Compose v2を対象とする。

## 9. S3保存

- `STORAGE_BACKEND=s3` の場合、ローカルと同じ論理構造を指定バケットの `S3_PREFIX` 配下へ保存する。
- raw JSON、正規化JSONL、取込状態、旧Analytics APIのraw JSONと状態をS3へ保存する。
- AWS認証情報はアプリへ保存せず、ECSタスクロールなどboto3の標準認証チェーンを利用する。
- 必要なS3権限は対象プレフィックスの `GetObject`、`PutObject` と、raw履歴取得のための `ListBucket` とする。
- 正規化JSONLはread-modify-writeで更新するため、複数ライターによる同時更新は対象外とする。
- S3障害時はローカルへ暗黙にフォールバックせず、リクエストを失敗させて不整合を防ぐ。
